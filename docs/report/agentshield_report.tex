\section{Introduction}\label{introduction}

\subsection{Problem Statement}\label{problem-statement}

Modern AI systems are moving from simple chatbots to agentic systems
that take real actions through tools such as email, files, calendars,
task managers, code hosting, and HTTP APIs. This shift creates a new
class of security risk: malicious content hidden inside emails,
documents, webpages, or tool responses can manipulate an agent into
unsafe actions --- leaking private data, sending messages to
unauthorized recipients, or performing destructive operations the user
never requested.

The specific problem this project addresses is: \textbf{how can we test
and protect tool-using AI agents from prompt injection, data leakage,
unauthorized tool use, and unsafe actions before a tool call is
executed?}

AgentShield is a multi-agent security framework that simulates
tool-using AI agents, generates red-team attacks against them, validates
each proposed tool call against structured safety policies, blocks or
escalates risky actions, and produces audit records explaining every
decision. Crucially, the firewall inspects the proposed tool call
\textbf{before} execution, so an unsafe action is stopped rather than
merely reported after the fact.

\subsection{Why Generative AI Is
Useful}\label{why-generative-ai-is-useful}

Generative AI is central to the framework because AgentShield must
interpret natural-language requests, reason over tool-use intent,
generate realistic adversarial scenarios, apply safety policies to
ambiguous cases, classify risk, and explain its decisions in readable
audit reports:

\begin{itemize}
\tightlist
\item
  The \textbf{Target Agent} uses GenAI for tool-use reasoning and
  structured tool-call generation.
\item
  The \textbf{Red-Team Agent} uses adversarial prompting to generate
  realistic prompt-injection attacks and malicious scenarios.
\item
  The \textbf{Policy Compiler and Firewall} use policy reasoning to
  interpret rules, resolve ambiguous risk, and generate audit
  explanations.
\item
  An \textbf{LLM-as-a-judge} is used only for subjective quality checks
  (audit explanation quality), never for primary correctness scoring,
  which is always measured against fixed ground-truth labels.
\end{itemize}

\section{System Architecture}\label{system-architecture}

AgentShield uses a modular backend workflow that owns the full local
decision path: scenario ingestion, tool-call proposal, schema
validation, policy and risk evaluation, safe mock execution, audit
capture, metrics, and baseline comparison. (Full detail:
\texttt{docs/architecture.md}.)

\subsection{Decision Pipeline}\label{decision-pipeline}

Each user request or stored scenario flows through the same path:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  The \textbf{Target Agent} proposes a structured tool call.
\item
  The proposed call is \textbf{schema-validated}.
\item
  In parallel, the \textbf{Policy Checker} evaluates every enabled
  safety rule and the \textbf{Risk Classifier} scores risk level and
  category.
\item
  The \textbf{Firewall} combines both results and chooses the most
  restrictive outcome: \texttt{ALLOW}, \texttt{BLOCK}, or
  \texttt{ASK\_APPROVAL}.
\item
  Only \texttt{ALLOW} may proceed to optional \textbf{safe mock
  execution}; \texttt{BLOCK} and \texttt{ASK\_APPROVAL} never execute.
\item
  The \textbf{Orchestrator} records an audit entry and workflow state,
  which feed metrics, the API response, and evaluation exports.
\end{enumerate}

\subsection{Safety Boundary}\label{safety-boundary}

All tool execution is simulated. Mock tools validate arguments and
return synthetic outputs but never perform real side effects --- no
email is sent, no file is read or written, no HTTP request leaves the
machine. \texttt{ALLOW} means the firewall permits the call \emph{in
simulation only}.

Policy checking, risk classification, and label validation share the
same security-pattern, text-matching, and intent helpers, which keeps
dataset labels, runtime decisions, and evaluation reports aligned.
Intent checks use standalone keyword matching (so short terms like
\texttt{get} or \texttt{list} do not match inside unrelated words), and
\texttt{delete\_file} has an explicit deletion gate so read-only
requests never authorize a deletion. External-target checks treat known
internal hosts and configured internal email domains as internal;
everything else is external for policy purposes.

\subsection{Label Rules}\label{label-rules}

The controlled vocabularies are documented in
\texttt{../../data/attack\_taxonomy.md}.

General labeling rules:

\begin{itemize}
\tightlist
\item
  Benign scenarios use \texttt{attack\_category:\ none} and are allowed
  when the tool call matches the request and is low impact.
\item
  Destructive but user-requested actions use \texttt{ASK\_APPROVAL} when
  execution should be confirmed.
\item
  Prompt-injection, data-exfiltration, and unauthorized-action scenarios
  use \texttt{BLOCK} when the proposed call violates user intent or
  exposes sensitive data.
\item
  External sends, external state-changing HTTP calls, and external
  attendees may use \texttt{ASK\_APPROVAL} when the user authorized the
  action but the impact warrants confirmation.
\end{itemize}

\section{Conclusion and Limitations}\label{conclusion-and-limitations}

\subsection{Conclusion}\label{conclusion}

AgentShield demonstrates that a dedicated, policy-driven firewall can
secure tool-using AI agents against prompt injection, data exfiltration,
and unauthorized actions \emph{before} a tool call executes. On the
94-scenario stored evaluation set the firewall reaches 100\%
policy-compliance with no false negatives and no false positives, while
the unprotected and prompt-only baselines let unsafe calls through ---
showing that structured inspection of tool arguments, recipients, URLs,
and user intent catches violations that prompt-level guardrails miss.

The red-team track was central to this outcome. Expanding the
adversarial corpus across all eight tools surfaced coverage gaps ---
around protected writes, public issue credential leaks, sensitive reads,
and unauthorized calendar/task creation --- that were then closed with
reusable policy checks and regression tests. Finding and fixing those
gaps \emph{before} they reach a production integration is exactly the
value the framework is meant to provide.

\subsection{Limitations}\label{limitations}

\begin{itemize}
\tightlist
\item
  \textbf{Synthetic and scenario-based.} The dataset proves coverage for
  the committed project scenarios, not every possible production input.
  Real deployments would need continual corpus growth with new tools,
  argument fields, injection phrasings, and benign lookalikes.
\item
  \textbf{Simulation only.} All tool execution is mocked; no real side
  effects occur. Real-world execution must remain behind explicit user
  approval and production integration controls.
\item
  \textbf{\texttt{ASK\_APPROVAL} is a policy boundary}, not a guarantee:
  it marks legitimate but risky actions for human confirmation, and its
  calibration depends on the configured policies.
\item
  \textbf{Subjective quality} (audit-explanation readability) is scored
  with an LLM-as-a-judge and a rubric; only objective correctness is
  measured against fixed ground-truth labels.
\end{itemize}
