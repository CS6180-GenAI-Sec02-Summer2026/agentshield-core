\section{Problem Definition and GenAI
Fit}\label{problem-definition-and-genai-fit}

\subsection{Problem Statement}\label{problem-statement}

Modern AI systems are moving from chatbots to \emph{agentic}
systems that take real actions through tools such as email,
files, calendars, task managers, code hosting, and HTTP
APIs. This shift introduces a new class of security risk:
malicious content hidden inside emails, documents, webpages,
or tool responses can manipulate an agent into unsafe
actions --- leaking private data, messaging unauthorized
recipients, or performing destructive operations the user
never requested.

The problem this project addresses is: \textbf{how can we
test and protect tool-using AI agents from prompt injection,
data leakage, unauthorized tool use, and unsafe actions
before a tool call is executed?}

AgentShield is a multi-agent security framework that
simulates tool-using agents, generates red-team attacks
against them, validates each proposed tool call against
structured safety policies, and blocks or escalates risky
actions with an audit trail. The firewall inspects the
proposed call \textbf{before} execution, so an unsafe action
is \emph{stopped}, not merely reported afterward.

\subsection{Generative AI Fit and Implementation
Boundary}\label{generative-ai-fit-and-implementation-boundary}

Generative models are relevant to future versions of this
problem because model-backed agents can interpret open-ended
requests, propose structured tool calls, generate adversarial
variants, and assist with subjective explanation review. The
checked-in implementation is deliberately different: it is a
deterministic, offline reference system with no external model
or API dependency. This boundary keeps the current evaluation
repeatable and must not be confused with implemented
model-backed behavior.

\section{Application and Technical Depth of Implemented
Techniques}\label{application-and-technical-depth-of-implemented-techniques}

\subsection{Decision Pipeline}\label{decision-pipeline}

Each request or stored scenario flows through one path: the
\textbf{Target Agent} proposes a structured tool call; the
call is schema-validated; the \textbf{Risk Classifier}
assigns risk metadata; the \textbf{Policy Checker} evaluates
all applicable rules; and the \textbf{Firewall} uses the most
restrictive policy violation to select \texttt{ALLOW},
\texttt{BLOCK}, or \texttt{ASK\_APPROVAL}. The risk result is
included in the explanation and audit record but does not
override the policy decision. Only \texttt{ALLOW} may reach
optional safe mock execution, and the \textbf{Orchestrator}
records the result for metrics and the API.

dataset. It renders attack \emph{seeds} into schema-valid
adversarial scenarios and delivers hidden directives through

\subsection{Policy Reasoning and Audit
Explanations}\label{policy-reasoning-and-audit-explanations}

The Policy Compiler parses a constrained Markdown policy
format using explicit fields and keyword mappings, then
exports structured JSON rules. The Policy Checker evaluates
those rules, the Risk Classifier independently applies
deterministic risk signals, and the Firewall renders a
human-readable explanation from the matched policy evidence
and risk metadata. The most restrictive matched policy rule,
not the risk score, determines the final decision.

Audit quality has two separate deterministic proxy measures.
The runtime pipeline records a 1--3 field derived from label
agreement and explanation presence; it is not an independent
review of explanation quality. The offline five-criterion
heuristic scores the checked-in dataset explanation fields
from 0--10 using lexical and grounding proxies. The current
\texttt{audit\_scores.json} therefore contains neither model
judgments nor scores over runtime audit logs.

\subsection{Schema and Knowledge
Sources}\label{schema-and-knowledge-sources}

Every scenario follows \texttt{dataset\_schema.json} with
seven required fields: \texttt{user\_request},
\texttt{external\_context} (external content that may carry
injected instructions), \texttt{proposed\_tool\_call},
\texttt{expected\_decision} (\texttt{ALLOW} / \texttt{BLOCK}
/ \texttt{ASK\_APPROVAL}), \texttt{risk\_level},
\texttt{attack\_category} (\texttt{none},
\texttt{prompt\_injection}, \texttt{data\_exfiltration},
\texttt{unauthorized\_action}), and \texttt{explanation}.
An optional \texttt{id} property supports lookup. Explicit
and loader-generated IDs use the \texttt{sample-*},
\texttt{v0-*}, \texttt{rt-*}, \texttt{be-*}, and
\texttt{demo-*} prefixes. The controlled label vocabulary is
documented in \texttt{data/attack\_taxonomy.md}.

All eight supported tools are represented:

\subsection{Dataset Quality}\label{dataset-quality}

Quality is checked with version-controlled utilities.
\path{validate_dataset.py} checks a specified dataset file
against the schema. \path{corpus_report.py} checks schema
validity and duplicate requests within the 85-example corpus;
\path{quality_report.py} reports balance and 12
approval-labeled cases for manual review; and
\path{label_validator.py} confirms labels agree with
runtime firewall behavior using the same shared helpers.
That last check detects implementation-label drift but is not
an independent adjudication of the labels.
The corpus-level duplicate check does not include the demo
or sample sets, which is why it does not detect the
94-entry-set duplicate. Representative checks are:

\begin{verbatim}
PYTHONPATH=. python3 data/validate_dataset.py data/dataset_v0.json
PYTHONPATH=. python3 data/corpus_report.py
PYTHONPATH=. python3 data/quality_report.py
\end{verbatim}

\subsection{Implemented Scope}
\label{implemented-scope}

The original plan targeted 150--300 examples and identified
100--150 as a reduced scope. The checked-in implementation
contains 94 stored entries, or 93 unique requests, including
an 85-example evaluation corpus. This is below both planned
size ranges. Coverage remains broad across all eight tools,
all three decisions, all four risk levels, and all attack
categories, but the smaller synthetic set limits claims of
generalization.

\subsection{Synthetic-Data
Boundary}\label{synthetic-data-boundary}

All dataset content is synthetic. Email addresses use the
reserved \texttt{.example} domain, secret-like values use marked
\texttt{\textless{}synthetic-...-placeholder\textgreater{}}
tokens, and focused tests scan the generated red-team set
and benign edge cases for non-synthetic emails or plausible
secrets. The repository does not currently provide one
global sensitive-data scan covering every dataset file.

\section{Evaluation Pipeline}\label{evaluation-pipeline}

\subsection{Method}\label{method}

Evaluation runs every stored scenario through the same
policy checker, risk classifier, intent helpers, and
firewall decision path used by the live API, then compares
each decision to the scenario's \texttt{expected\_decision}
label. This produces a deterministic, repeatable consistency
measurement against the checked-in reference labels; it is
not independent evidence that those labels generalize to
production. In the implemented metric
terminology, ``malicious'' means expected \texttt{BLOCK},
``benign'' means expected \texttt{ALLOW}, and
approval-labeled entries form a separate class even when an
attack category is present.

\subsection{Metrics}\label{metrics}

The pipeline reports Attack Success Rate, Defense Success
Rate, Benign Task Success Rate, False Positive / False
Negative Rate, Policy Compliance Accuracy, \texttt{BLOCK}
precision/recall/F1, escalation rate, tool-call integrity,
and runtime audit-explanation quality. In the current runner,
the tool-call-integrity flag is supplied as \texttt{true} for
every result rather than derived by an independent intent
comparison, so its reported 100\% is an instrumentation
default. Runtime audit quality is likewise the agreement and
presence proxy described above. A separate offline 0--10
heuristic evaluates dataset explanation text; the two
audit-quality scales measure different artifacts and must
not be combined.

\subsection{Reproduction}\label{reproduction}

The experiment runner regenerates
\path{data/evaluation/experiment_run.json} and its summary
CSV, including runtime metrics and a nested baseline
comparison:

\begin{verbatim}
PYTHONPATH=. python3 src/experiment_runner.py
\end{verbatim}

Additional validation and audit scoring are run separately:

\begin{verbatim}
PYTHONPATH=. python3 -m pytest -q
PYTHONPATH=. python3 data/corpus_report.py
PYTHONPATH=. python3 src/label_validator.py --rules data/policy_rules.json --test
PYTHONPATH=. python3 agents/score_audit.py
\end{verbatim}

The two PNG figures are checked-in presentation artifacts;
the repository does not currently include a chart-generation
script. From \texttt{docs/report}, this TeX source can be
compiled with two XeLaTeX passes:

\begin{verbatim}
xelatex -interaction=nonstopmode -halt-on-error agentshield_report.tex
xelatex -interaction=nonstopmode -halt-on-error agentshield_report.tex
\end{verbatim}

red-team track provides.

\section{Conclusion and
Limitations}\label{conclusion-and-limitations}

AgentShield demonstrates a deterministic, policy-driven
firewall that intercepts simulated tool calls before mock
execution. On the checked-in stored set it matches every
expected decision, while the unprotected and keyword
baselines allow many expected-\texttt{BLOCK} cases. The
adversarial corpus exposed policy gaps that were closed with
reusable checks and regression tests.

\textbf{Limitations.} The results are in-sample measurements
over a synthetic, policy-aligned set and do not establish
general production performance. The 94 stored entries contain
one exact duplicate and fall below the original dataset-size
targets. All tool execution is simulated. Model-backed target
reasoning, online attack generation, and online explanation
judging are unimplemented extension points. The offline
0--10 rubric currently scores dataset explanation fields,
not runtime audit logs. \texttt{ASK\_APPROVAL} is a policy
boundary whose calibration depends on configured rules.
Real deployment would require broader unseen evaluations,
global sensitive-data checks, authenticated integrations,
observability, and explicit human-approval controls.
